# HEALTH-CHECK — 專案健檢與建議（2026-10-24）

掃描範圍：`TKU-BridgeBook` 全部文件與程式碼（`src/`、`tests/`、`docs/`、CI、`vercel.json`）、正式站實際畫面、以及姊妹站 `TKU-BridgeTable` 的 `worker/book.ts`、`shared/protocol.ts`、PRD／ROADMAP 結構。結論分四段：做得好的、要改的、產品建議、推薦的處理順序。對應的 task 都已寫進 `docs/PRD/e*.md`。

## 1. 做得好的（維持）

| 項目 | 為什麼好 |
| --- | --- |
| **內容是結構化資料** | 叫品、意義、叫牌過程都是型別化資料（`types/convention.ts`），不是字串裡的表格。這是制度卡、自動出題、機器人同步三件事能做的前提。 |

## 2. 要改的（技術）

### 2.1 整本一頁、全部打包（最急）

- 現況：22 個特約靜態 import 進一個 bundle，`HandbookPage` 一次渲染全部；加入舊講義後 DOM 3.2 萬節點，展開全部 1.6 秒。
- 影響：制度集、文章、電子書、題庫進來後必然爆掉；手機記憶體也吃緊。
- 處理：`e10-t01`～`t05` 內容 manifest ＋按需載入、預建搜尋索引、service worker 按需快取；`e9-t04` 路由拆成「首頁／特約頁／全書目錄」。保留「印整本」給需要的人。

### 2.2 只有一套制度，分類寫死

- 現況：`CategoryId` 是型別列舉；`Convention` 沒有「種類／程度／誰採用」；線上只能「取代整個特約」。
- 影響：做不出「依隊伍／搭檔看」；新生與國手看同一份。
- 處理：E1 的 `kind`／`level`／`prerequisites`、分類即資料、`SystemProfile`（繼承 + 採用／不採用 + 列級覆寫 + 備忘）與純函式解析 `resolveProfile`。

### 2.3 線上版本與 `.ts` 檔兩個真相

- 現況：`ARCHITECTURE.md` §4.1「線上版本優先：改 `.ts` 不會顯示」。
- 影響：幹部改錯地方、Git 歷史不反映真實內容、備份靠記得。
- 處理：E8 的送審流程 ＋ `e8-t12`～`t14` 排程寫回 Git；之後 `src/content` 是初始資料與備份，線上為唯一真相。

### 2.4 治理

- 44 項待確認沒有負責人與狀態；任何 `bookEdit` 可直接發布；沒有審計。
- 處理：E8 全部（`bookReview` 權限、審核頁、diff、待確認面板、審計）。

### 2.5 兩個 repo 的型別脫鉤風險

- `lib/api.ts` 手抄牌桌 `shared/protocol.ts` 與 `worker/importer.ts` 的 schema，靠規則 9 提醒。
- 處理：`e10-t09` CI 從牌桌 repo 抓 `protocol.ts` 自動對拍；E7 的 `toSystemSpec` 放牌桌 `shared/`。

## 3. 要改的（介面）

正式站實際畫面（深色模式、`/c/lebensohl`）：

- **像工具不像書**：Swagger 式卡片堆＋多層手風琴，每張卡視覺重量一樣；分類標題只是小字。
- **與牌桌同色**：同一組淡江藍 token、同樣的頁首；社員在兩站間切換時分不出來。
- **頁首太擠**：七個圖示鈕（展開、收合、字級三段、主題、列印、安裝）＋搜尋＋帳號。
- **沒有入口**：首頁就是整本書；新生沒有「從哪開始」，社員沒有「我的制度」。
- **英文名稱與中文並列但層級不清**；標籤膠囊太多、顏色一致，變成雜訊。
- 好的部分：叫牌表清楚、四色花色、深層連結、待確認標示、手機抽屜。這些保留。

處理（2026-10-24 拍板）：配色與圓角保留為預設風格「一般」；加首頁（社團新聞、我的制度集、第一次來、最新討論）與個人設定（六種風格、四種版面、字體、字級、花色顏色、密度自選）。規格 `DESIGN-V2.md`，展示頁 `design/pitch.html`。

## 5. 推薦的處理順序

1. **先分片、再加欄位與制度集模型**（Phase A）：資料對了，後面都快。
2. **介面 v2 集中做完**（Phase B）：一次換皮，不混用。
3. **制度集編輯 → 隊伍與搭檔 → 制度卡**（Phase C、D）：這是 M1 的使用者價值。
4. **送審與待確認**（Phase F）：內容開始多人改之前。
5. M2 依「新生社課最急」排：分級 → 練習 → 叢書 → 牌桌整合 → 寫回 Git 與維運。

詳細批次在 `ROADMAP.md`；每批的開工指令在 `NEXT.md` 第 3 點。
