# PRD — TKU BridgeHall · 淡江橋館（原 TKU BridgeHall · 淡江橋館）

> 這是總 PRD。各 epic 的細節（AC、task）在同資料夾的 `e1`～`e10`，順序在 `docs/ROADMAP.md`，現在做到哪在 `docs/NEXT.md`。舊版 PRD（只有手冊功能 F1–F15）的內容已併入 §8.1。

## 1. 願景

**名稱（2026-10-24 決定）**：網站改名 **淡江橋館 · TKU BridgeHall**（原淡江橋譜 · TKU BridgeBook）。「館」收著橋譜、叢書，也是聚會討論的地方；**「橋譜」保留為館內「制度」區塊的名字**（首頁入口與路由 `/book` 仍叫橋譜），本文件其他地方的「橋譜段落」「橋譜內容」都指制度區塊。姊妹站淡江牌桌不變，兩站並稱「館／桌」。GitHub repo 2026-10-26 改為 `TKU-BridgeHall`，本機資料夾 2026-10-28 跟著改。

**一本活的橋譜。** 淡江橋藝社的制度、特約、信號、講義與叢書都在這裡，而且不是一份給全社團的死文件：每個隊伍、每對搭檔都能從社團制度長出自己的版本，一鍵印成制度卡；剛進社團的零基礎新生從「第一課」開始讀，打到國手的學長能查到最細的滿貫序列；姊妹站淡江牌桌的機器人照這本橋譜叫牌。

一句話：**橋譜是社團的制度資料庫、佈告欄與討論區，牌桌是拿制度來打牌的地方。** 討論區（牌局討論、社團新聞、個人檔案與頭像）先在橋譜給社內測試，好用再搬到牌桌開放全台灣橋手（牌桌 E13）。

## 2. 背景與問題

M0（2026-10-21～23 上線）解決了「Word 檔散落、版本對不上、手機看不了」：22 張特約卡片、搜尋、深層連結、線上編輯、AI 匯入、與牌桌共用帳號（§8.1）。還沒解決的：

| 問題 | 現況 |
| --- | --- |
| **只有一套制度** | 網站只有「社團制度」。一個隊伍 4–6 人、社團好幾隊，不同 pair 打不同的制度（有人 2/1、有人 1NT 15-17 有人 16-18、有人不打 Bergen），現在沒有地方記「我們這對打什麼」。 |
| **沒有程度分層** | 新生打開看到 2010 年講義、Jacoby 2NT 的 +1～+7 詢問叫和 Lebensohl 並排，不知道從哪裡開始；國手等級的人又嫌細節不夠。 |
| **制度卡還是手寫** | 比賽要交制度卡（convention card），每對搭檔還是自己開 Word 或抄範本。 |
| **只有「制度」，沒有「書」** | 主打、擠牌、防守等橋藝叢書和社課講義沒有地方放；社員還是在群組傳 PDF。 |
| **治理靠人** | 44 項「待確認」沒有負責人；線上版本與 `.ts` 檔兩個來源；沒有送審。 |
| **長得像工具，也像牌桌** | Swagger 式卡片堆、頁首七個圖示鈕、沒有首頁。2026-10-24 拍板：配色與圓角保留為預設「一般」，加首頁與個人設定（風格、版面、字體等自選）。 |
| **討論散在 FB 與 LINE** | 發一副牌要用全形空格排四家牌，叫牌過程只能一行一行打，過兩天就被洗掉；社團公告也沒有固定的地方。 |

## 3. 目標與非目標

**目標**

1. 制度集（System Profile）：社團制度是根，隊伍與搭檔可以繼承、覆寫、加註，網站依「我現在看哪一組」切換內容。
2. 制度卡：從任何制度集生成可印的制度卡（A4／PDF），比賽前五分鐘可以產出。
3. 分級：每份內容有程度標籤與導讀；新生有從零開始的路徑；高手有完整細節。
4. 叢書：文章與電子書的存放、分類與閱讀（主打、擠牌、防守、社課講義）。
5. 練習：從制度自動出叫牌題，自己練、也餵給牌桌的題庫。
6. 牌桌整合：制度集同步給牌桌機器人、牌桌的 Alert 連回橋譜段落。
7. 治理：待確認有負責人、修改走送審、線上內容定期備份回 Git。
8. 介面：預設保留現行配色與圓角（「一般」），另提供五種風格與四種版面讓每個人在個人設定自選；首頁有社團新聞、我的制度集、新生入口、最新討論（`docs/DESIGN-V2.md` §5.3、§10.5）。
9. 社群與討論：個人檔案與頭像、板面（公告、牌局討論、制度問答、閒聊）、對橋牌友善的貼文（四家牌、叫牌過程、單手牌、特約引用）、留言與反應、通知與管理；先社內，資料模型與牌桌 E13 共用（`e11`）。

**非目標**

- 不做打牌、不做即時聊天與私訊、不做比賽報名（牌桌與社務另有系統）。
- 討論區 M1 只給登入社員；公開瀏覽與多社團留給牌桌 E13／E12。
- 不做一般性的橋牌百科；收的是社團採用或推薦的內容。
- 不做公開的多社團平台（M3 以後視牌桌 E12 的結果再決定）。
- 不做 Markdown 編輯器；內容模型維持結構化區塊（有需要時加區塊種類）。

## 4. 使用者與角色

| 角色 | 需求 | 權限 |
| --- | --- | --- |
| 新生（零基礎） | 從第一課開始；看得懂每個名詞；知道社團「預設」打什麼 | 閱讀 |
| 社員 | 查自己這對搭檔的制度；練題；看叢書；印制度卡 | 閱讀、編自己的搭檔制度集 |
| 隊長 | 設定隊伍制度集、看隊內各 pair 的差異、印全隊制度卡 | `teamEdit`（自己的隊伍） |
| 制度負責幹部（編輯者） | 維護社團制度、處理待確認、審核送審、上傳叢書；使用者帳號以外的所有管理 | `bookEdit`、`bookImport`、`bookReview` |
| 管理員 | 全部，包括使用者帳號（與牌桌同一個管理介面） | 全部 |
| 牌桌機器人 | 讀制度集的結構化資料叫牌 | 系統 |

**角色規則**（使用者決定，2026-10-25；位階名稱先維持現狀，之後再改）：**管理員**可以管所有事情，包括使用者帳號；**編輯者**（`bookEdit`）可以管理除了使用者帳號以外的所有東西。

- 只限管理員（帳號）：申請與核准、新增與刪除帳號、重設密碼、管理員身分、勾選權限、社團設定（人數上限、邀請碼，決定誰能加入）。
- 編輯者也能做：編輯、隱藏、還原特約與版本紀錄；分類；制度集（新增、儲存、刪除、版本）；`/admin` 裡所有不是帳號的面板；關閉卡住的牌桌（牌桌 API）。之後新增的管理功能，不是帳號相關的就預設開給編輯者。
- `bookImport`（AI 匯入，會花 API 額度）、`boardCurate`（牌桌精選牌局）仍是個別勾選的權限，`bookEdit` 不包含；管理員都有。
- 每條 API 要什麼角色寫在牌桌 `worker/roles.ts`（ARCHITECTURE.md §4.2）。

## 5. 產品原則

1. **內容正確性第一**：逐字轉錄，疑義標「待確認」，不自行修正（沿用 `CLAUDE.md` 規則 1）。
2. **一份內容，多個視角**：制度集是「選擇與覆寫」，不是複製貼上；社團制度改了，所有繼承它的隊伍都看到。
3. **程度是標籤，不是分站**：同一篇內容用標籤與「入門版／完整版」切換服務兩端的人，不做兩個網站。
4. **結構化資料優先**：叫品、意義、牌例都是資料，所以能生成制度卡、出題、同步給機器人；純文字只在文章。
5. **像一本書**：閱讀為主、工具退後；每一頁都能印、都能分享。
6. **與牌桌分工**：帳號、通知、檔案儲存共用牌桌的 Worker；橋譜只做內容。

## 7. 使用者故事

**新生**

1. 我第一次打開網站，想知道「社團打什麼制度」和「我該先學什麼」，而不是 22 張卡片。
2. 看到「NMF」「GF」「splinter」這些字，我想點一下就有解釋。
3. 我想先看「入門版」：只有開叫、答叫和幾個最常用的特約，進階段落先收起來。

**社員與搭檔**

4. 我和搭檔打 1NT 16-18 而不是社團的 15-17，我想在「我們的制度」裡改這一條，其他都跟社團一樣。
5. 比賽前我想一鍵印出我們這對的制度卡。
6. 我想在某一段加一條只有我們兩個看得到的備忘（「這裡我們約好叫 3♣」）。
7. 我想抽 20 題「我們制度」的叫牌題，打牌前複習。

**隊長**

8. 我想看隊上三對搭檔的制度差在哪裡，決定要不要統一。
9. 新隊員加入，我想把他和搭檔的制度集直接從隊伍制度集複製一份。

**幹部**

10. 我改了社團制度的 1NT 答叫，想知道有哪些隊伍覆寫過這段、要不要通知他們。
11. 社員送來一份修改，我想看差異再決定發布。
12. 我想上傳一本社課講義 PDF 和一篇主打文章，放進「叢書 › 做莊技巧」。
13. 我想把 44 項待確認一項一項分派、關掉。

**社群**

16. 我想發一副今天社課的牌，四家牌和叫牌過程直接排好，不用再對齊空格；大家在下面留言討論該怎麼叫。
17. 我想在首頁看到社團公告（比賽報名、社課時間）和最新的討論，不用翻 LINE。
18. 我想有自己的頭像和介紹，牌桌上的名牌也用同一個。
19. 身為幹部，我想發公告並置頂，有人亂發可以刪、可以鎖。

**高手與牌桌**

14. 我在牌桌上看到機器人 Alert「轉換♥」，想點一下跳到橋譜的那一段。
15. 我想確定牌桌的淡江機器人叫的和橋譜寫的一樣。

## 9. 非功能需求

- **正確性**：內容測試（`tests/content`）擴到制度集與制度卡：繼承後的制度集仍通過 schema；制度卡每一格都能追溯到段落。
- **效能**：首頁 JS gzip ≤ 150 kB；任一特約頁 ≤ 1.5 秒可互動（4G）；展開全部不再是常態操作（E9 改每特約一頁）。
- **離線**：已讀過的特約、我的制度集與制度卡離線可看。
- **無障礙**：維持 WCAG AA；花色不只靠顏色；鍵盤可操作所有收合；程度與覆寫標記有文字。
- **安全**：隊伍與搭檔的制度集只有成員可編輯；私人備忘只有該搭檔看得到；電子書依授權欄位限制可見範圍。
- **成本**：維持 Vercel 免費方案與牌桌的 Cloudflare 免費方案；R2 免費額度 10 GB；AI 匯入與出題用社團額度並顯示估價。
- **語言**：繁體中文（台灣）；橋牌術語可保留英文。

## 13. 風險

| 風險 | 對策 |
| --- | --- |
| 制度集的覆寫模型太複雜，社員不會用 | 覆寫只有兩種粒度：整個特約「採用／不採用」、單一叫品列或段落「改成」；其餘用備忘。先做搭檔這一層，再做隊伍。 |
| 內容增多後整頁 DOM 爆掉 | E10 分片與 E9 每特約一頁在 M1 最前面做。 |
| 後端都在牌桌的 Worker，兩邊 schema 容易脫鉤 | `shared/protocol.ts` 是唯一來源；橋譜 `lib/api.ts` 有型別對拍測試；每個改 API 的 PR 兩邊一起開。 |
| 電子書版權 | 上傳必填授權欄位（自撰／取得授權／僅社內）；僅社內的只有登入社員可看；不放未授權的商業書。 |
| 制度卡格式（WBF／CTCBA）不一致 | 先做 WBF 標準欄位與社團簡式兩種；台灣賽制的卡用簡式印。 |
| 設計改版打斷功能開發 | 預設風格「一般」沿用現行 token，E9 的工作是加風格維度與首頁，不是換皮；其他風格只是 token 組。 |
| 討論區在橋譜與牌桌做兩次 | 型別與 Worker 模組一開始就放牌桌 repo（`shared/forum.ts`、`worker/forum.ts`），橋譜只是第一個前端；搬家時只搬 UI。 |
