## 背景

M0 的治理靠人：44 項「待確認」沒有負責人與狀態；線上版本與 `.ts` 檔是兩個真相（`ARCHITECTURE.md` §4.1「線上版本優先」）；任何有 `bookEdit` 的人按「儲存並發布」就上線，沒有第二人看過；改了也沒人知道。制度是社團的共同約定，需要「誰確認、誰審核、改了什麼、通知誰」。

## 目標

- **送審**：編輯存草稿 → 送審 → 審核者（`bookReview`）看差異 → 發布或退回；`club` 制度集與內建特約必走送審，隊伍與搭檔制度集不必。
- **待確認面板**：所有 `pending` 集中管理：指派、狀態（未處理／處理中／已確認／擱置）、關閉時記錄誰與依據。
- **版本差異**：任兩版段落級 diff（叫品列、條列、段落）。
- **寫回 Git**：線上內容成為唯一真相；排程把線上內容輸出成 `.ts`／JSON 開 PR 當備份與審計；`.ts` 不再手改。
- **變更通知**：發布後通知訂閱者（搭檔制度集的成員、覆寫過該段的隊伍）走牌桌通知中心。
- **審計**：誰在何時改了什麼，可查。

## 非目標

- 不做複雜的多級審核；一位審核者即可。
- 不做 Git 整合到瀏覽器（寫回由 CI 做）。

## 需求

### 功能

- 狀態機：`draft → in-review → published`，退回回 `draft`；`BookEntry` 加 `status`、`reviewRequestedBy/At`、`reviewedBy/At`、`reviewNote`。
- 審核頁 `/review`：待審清單、差異、發布／退回（附理由）；發布時寫版本與審計。
- 待確認：`pending` 欄位保留在內容裡（顯示用），另存 `pendingmeta:<slug>/<sectionId>/<n>`（指派、狀態、備註、關閉依據）；面板 `/pending` 取代側欄的簡單清單；關閉時要同時修改內容（走送審）。
- Diff：`lib/diff.ts`，以段落 id 對齊，叫品列以 `call` 對齊，產生新增／刪除／修改三種；UI 左右對照或行內。
- 寫回：GitHub Action 每週（或手動）呼叫 `GET /api/book/export`（JSON＋生成的 `.ts`），有差異就開 PR 到 `content-backup` 分支；`README.md` 改寫「內容的真相在線上，`src/content` 是初始資料與備份」。
- 通知：發布事件 → `notifications.notify(userIds, 'book:published', { slug, version, summary })`；訂閱＝搭檔或隊伍制度集採用該特約、或使用者手動「關注」。
- 審計：`audit:<time>-<id>`（誰、動作、對象、版本）；管理頁可查最近 200 筆。

### 非功能

- 送審不影響閱讀效能（讀者只拿 `published`）。
- 寫回的 `.ts` 必須通過 `tests/content`（CI 跑一次），不通過就不開 PR 並通知。

## 設計方向

- 編輯器的「儲存並發布」改為「儲存草稿」＋「送審」（有 `bookReview` 的人多一個「直接發布」）；隊伍與搭檔制度集維持直接儲存。
- 待確認面板的每一列：位置（深層連結）、原文、問題、負責人、狀態、備註；可用篩選「我的」。
- 通知文案用現有 `strings.ts` 格式；牌桌端通知種類加 `book:published`、`book:review-requested`、`book:suggest-unify`（E2）。
